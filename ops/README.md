# ops/ — deployment runbook

Operational guide for running the Tennis Prediction Bot pipelines on Windows and
scheduling the daily prediction run. The pipeline code is feature-complete; this
directory holds the thin deployment glue (env loading, mirror sync, the two
wrappers, and the Task Scheduler definition). Ground truth for behaviour is
`DECISIONS.md`; this file is operational only.

## Contents

| File | Purpose |
|---|---|
| `lib.ps1` | Shared helpers: `Import-DotEnv` (robust `.env` loader), `Sync-SackmannMirror`, `Invoke-Tennis`. Dot-source it; contains no secrets. |
| `run_train.ps1` | Wrapper: load env -> sync mirror -> `python -m tennis train`. |
| `run_daily.ps1` | Wrapper: load env -> sync mirror -> `python -m tennis run`. The 06:30 UTC cron entrypoint. |
| `tennis-run.xml` | Windows Task Scheduler definition for the daily run at 06:30 UTC. NOT auto-registered. |
| `alembic.ini` | Alembic config (DB URL injected from `DATABASE_URL` at runtime). |

## The two pipelines

- `python -m tennis train` — Data -> Research(training) -> Modeling(training).
  Ingests Sackmann history, builds the training feature matrix, trains and
  **registers + activates** a model. Run on demand or a slow cron. **It is the
  prerequisite for the daily run** (bootstrap, DECISIONS.md S6).
- `python -m tennis run` — Data -> Research(prediction) -> Modeling(prediction)
  -> Briefing -> Monitor. The daily 06:30 UTC prediction chain. Fails fast with
  `no_active_model` until a model has been trained (S6).

Exit code (S8): `1` iff some agent that ran ended `failed`; `partial`,
`succeeded`, and a lock-already-held no-op all exit `0`.

## One-time setup

1. **Python env** (from the repo root):
   ```powershell
   py -3.12 -m venv .venv
   .\.venv\Scripts\python.exe -m pip install -e ".[dev]"
   ```
2. **`.env`** at the repo root (gitignored — never commit it). Required keys:
   `DATABASE_URL`, `ODDS_API_KEY`, `OPENWEATHER_API_KEY`, `ANTHROPIC_API_KEY`,
   `SMTP_HOST`, `SMTP_USER`, `SMTP_PASSWORD`, `BRIEFING_RECIPIENTS`. (Training
   needs only `DATABASE_URL` + the four adapter keys; the daily run also needs
   Anthropic + SMTP + recipients.)
   - **The app does NOT autoload `.env`** — it reads `os.environ` directly. Every
     invocation must export it first. `Import-DotEnv` in `lib.ps1` does this and
     correctly handles inline `# comments` and values with spaces (the Gmail app
     password). The `Invoke-Tennis` wrapper calls it for you.
3. **Database migrations** (run from the repo root):
   ```powershell
   . .\ops\lib.ps1; Import-DotEnv
   .\.venv\Scripts\alembic.exe -c ops\alembic.ini upgrade head
   ```
   This creates all tables (incl. `briefing_deliveries`). `alembic.ini` anchors
   its `script_location` with `%(here)s`, so it works from any working directory.
4. **Sackmann mirror** — a git clone of `JeffSackmann/tennis_atp` on disk at
   `config.sources.sackmann.local_mirror_dir`. `scripts/sync_sackmann_mirror.py`
   clones it (and on later runs fast-forwards + refreshes the dir mtime so the
   staleness pre-flight, C5, stays happy). The wrappers sync automatically; to do
   it by hand:
   ```powershell
   $env:PYTHONPATH = "src"; .\.venv\Scripts\python.exe scripts\sync_sackmann_mirror.py
   ```
5. **`config/venue_coords.yaml`** — static venue coordinates (L11), already
   generated by `scripts/geocode_venues.py`. The DataAgent upserts these so the
   weather step has coord-bearing venues; a missing file degrades gracefully.

## Bootstrap order (first deploy)

```powershell
.\ops\run_train.ps1      # train + activate a model (long; see below)
.\ops\run_daily.ps1      # then the daily prediction chain
```

## First train is a long, resumable backfill

The first `train` ingests the full `ingestion.history_backfill_season_range`
(default 2000-2026) into Postgres. Writes are **per-row** (insert + read-back +
commit). Against a **remote** Postgres (e.g. Supabase) this measured ~80 ms per
row, so the first full backfill is a **multi-hour job** (players file alone is
~65k rows ≈ 90 min). Treat it as a detached / overnight operation.

- **It is resumable.** Players upsert is `ON CONFLICT`; each season is watermarked
  `complete` and skipped on re-run; a killed run leaves a `running` row that the
  next run's orphan sweep reaps. So you can run `run_train.ps1` repeatedly until
  it finishes.
- **For a faster first / smoke train**, narrow
  `ingestion.history_backfill_season_range` in a copy of `config.yaml` and pass it
  with `--config` (e.g. `Invoke-Tennis -Command train -ConfigPath .\config\config.smoke.yaml`),
  then widen it for the production model.
- **Daily prediction runs are fast** — they only write the day's small slate; the
  big-write cost is unique to the historical training backfill. A future storage
  optimization (bulk/`COPY` inserts, dropping the read-back) would cut the backfill
  dramatically.

## Known limitation: the ATP scraper is Cloudflare-blocked

`atptour.com` is behind Cloudflare bot management and returns **HTTP 403 even
with a real browser User-Agent** (a JS-challenge interstitial, no match HTML). The
fixture-validated selectors in `adapters/atp_scraper/parser.py` therefore cannot
be re-derived from live HTML (K5/K6), and the scraper supplies no live slate.

- **Training is unaffected** (S6a): the training chain builds the DataAgent with
  `scraper_required=False`, so a scraper failure no longer drops Data to `partial`
  or blocks Research/Modeling. Training uses Sackmann `final` history only.
- **The daily run still needs the scraper** for a non-empty prediction slate. Until
  it is solved the daily chain ingests no upcoming matches, so it produces no
  predictions and sends no briefing (N4 zero-email).
- **Remediation paths** (future extensions, out of scope here): a headless browser
  (Playwright is already a dependency) to pass the JS challenge, a Cloudflare-bypass
  service, or an official ATP/data-feed source for the slate.

## Reading a run's outcome

Each agent stage is a row in `pipeline_runs` keyed `(run_id, agent, attempt)`; all
stages of one invocation share a `run_id`.

```sql
select run_id, agent, status, started_at, finished_at,
       error, metrics
from pipeline_runs
order by started_at desc
limit 20;
```

- **succeeded** — the stage met its full success contract.
- **partial** — it ran but degraded (e.g. an adapter had failures, calibration
  degraded, Monitor lacked enough data). The daily run still exits `0`.
- **failed** — a fatal stage error (`error` JSONB has the redacted cause/code). A
  not-met precondition writes **no row** (the stage is skipped, not failed) — so a
  missing `research`/`modeling` row after a `partial` Data is expected.
- `monitor` runs regardless of upstream status (A13) and writes ECE/PSI/ROI into
  `pipeline_runs.metrics` (Q6).

## Scheduling the daily run (06:30 UTC)

`tennis-run.xml` defines the task but is **not registered automatically**
(deployment is environment-specific, S7). The `StartBoundary` ends with `Z`, so it
fires at 06:30 **UTC** regardless of local timezone/DST.

Register (PowerShell, encoding-safe):
```powershell
Register-ScheduledTask -TaskName "tennis-run" `
  -Xml (Get-Content -Raw .\ops\tennis-run.xml)
```
Or with `schtasks`:
```powershell
schtasks /Create /TN "tennis-run" /XML ".\ops\tennis-run.xml"
```

The XML's principal uses `InteractiveToken` (runs only while the account is logged
on, no stored password). To run whether logged on or not, register with explicit
credentials:
```powershell
Register-ScheduledTask -TaskName "tennis-run" `
  -Xml (Get-Content -Raw .\ops\tennis-run.xml) `
  -User "Andrew" -Password (Read-Host -AsSecureString "Password")
```

Inspect / run-now / unregister:
```powershell
Get-ScheduledTask -TaskName "tennis-run"
Start-ScheduledTask -TaskName "tennis-run"          # run on demand
Get-ScheduledTaskInfo -TaskName "tennis-run"        # LastRunResult = exit code
Unregister-ScheduledTask -TaskName "tennis-run" -Confirm:$false
```

For the (less frequent) training job, register a second task that runs
`ops\run_train.ps1` instead of `run_daily.ps1` — copy `tennis-run.xml`, change the
`-File` argument and the `<URI>`, and pick a cadence (e.g. weekly). Adjust the
absolute repo path in the XML if the checkout lives elsewhere.

## Security

`.env` holds real secrets and is gitignored — never commit it. The ops scripts
read secrets from `.env` at runtime and contain none themselves.
